# Hansard — DPS Season Manager

A Discord bot + Fastify API + React webapp for managing Dynamic Political Simulation seasons.

## Project Structure

TypeScript monorepo with pnpm workspaces:
- `packages/db` — Drizzle ORM schema + PostgreSQL migrations
- `packages/shared` — Shared types, constants, status enums
- `packages/bot` — discord.js v14 Discord bot
- `packages/api` — Fastify REST API
- `packages/web` — React 18 + Vite + TanStack Router SPA
- `packages/mcp` — Model Context Protocol server exposing read-only tools to LLM clients

## Key Design Decisions

- **The bot is a ledger, not an enforcer.** It tracks what's happening, helps find information, automates tedious bits. The actual political gameplay stays fluid and human-driven.
- **Bot display name is configurable** via `BOT_DISPLAY_NAME` env var (defaults to "Hansard").
- **Warm serif aesthetic** — Crimson Pro for headings, Lora for body text, JetBrains Mono for data. No sans-serif body text. Warm cream backgrounds, terracotta accent. Parliamentary record feel, not SaaS.
- **Theming via CSS variables, not Tailwind `dark:` utilities.** Tailwind colour tokens (`page`, `card`, `text-primary`, `c-bills`, etc. in `packages/web/tailwind.config.ts`) all reference `var(--token)` defined in `packages/web/src/main.css` under `:root` (light) and `[data-theme='dark']` (warm chamber palette — walnut-black page, leather-bound cards, terracotta lifted to `#E89478`, all module accents shifted ~12-18% L). Components keep using `bg-page`, `text-text-primary`, etc. — no `dark:` variants needed. Toggle lives in `ThemeProvider` (`packages/web/src/components/theme/ThemeProvider.tsx`); preference persists to `localStorage['hansard-theme']` as `'light' | 'dark' | 'system'`. An inline script in `packages/web/index.html` applies `data-theme` to `<html>` before React hydrates to avoid a white flash on dark refresh — keep its storage key and resolution logic in sync with the provider. UserMenu hosts the Light/Dark/System pill switch.
- **Voting algorithms** use a strategy pattern (`TallyStrategy` interface) for 8 methods: FPTP, ranked choice, STV, approval, proportional, yea/nay, two-round runoff, exhaustive ballot.
- **Yea/nay supermajority means exact two-thirds of yea+nay votes.** Abstentions count in turnout but are excluded from the pass denominator. Use `SUPERMAJORITY_PASS_THRESHOLD` / `meetsVoteThreshold` from `@hansard/shared` rather than rounded literals; legacy persisted `0.667` configs are normalized to exact `2 / 3` for tallying.
- **Circular DB references** — some cross-table references (bills↔elections, players↔offices) are stored as plain uuid columns without FK constraints to avoid circular import issues. Linked at query time.
- **Auth flow** — Discord OAuth via `/api/auth/discord` → callback looks up player by `discord_id`, **auto-creates an active player** if absent, aggregates `permissions` from current office holdings (`office_holders` joined to `offices.permissions`). `session.user.id` is `players.id` (UUID), NOT the Discord snowflake. `requireAuth` middleware refetches the player on every request and populates `request.player` for handlers.
- **OAuth player rows are not necessarily characters.** OAuth/device login can create an active `players` row with `characterName = null`; character-facing rosters, typeaheads, public player lists, member counts, office/party eligibility, voting denominators, candidate registration, and reaction ballots should require `players.characterName IS NOT NULL` unless the feature explicitly wants auth identities. `/player roster` and shared `listPlayers` already apply this guard so placeholder login rows do not render as `(unnamed)` independents.
- **Invite-only parties are staff-assigned.** `parties.is_invite_only` blocks public/self-service membership paths (`/party join`, API self party changes, and `/character create` party picker) while staff assignment remains the invite mechanism via `/player admin change-party` or staff API updates. Roll out the column with `pnpm --filter @hansard/db migrate:invite-only-parties` before deploying code that reads it.
- **Frontend gating** — `useAuth()` (TanStack Query wrapper around `/api/auth/me` with `retry: false`) returns `{ user, isStaff, permissions, hasPermission, logout, isLoading }`. Three patterns: route-level `<RouteGuard requireStaff>`, section-level `{isStaff && ...}`, button-level `{hasPermission('x') && ...}`. Backend remains source of truth — frontend gating is for UX. Because the auth query is cached with `staleTime: Infinity`, `AuthProvider` must clear `AUTH_QUERY_KEY` when any protected query fails with an `ApiError` 401; otherwise stale client auth can leave protected pages rendering raw `Authentication required` payloads instead of redirecting to `/login`.
- **Player-facing metadata must be public-only.** The dashboard home route is available to every authenticated player, so `/api/dashboard/*` must branch on `request.player.isStaff`: staff can see ticket/moderation counts, draft votes, and private operational activity; players must receive only public metrics and public activity. Do not rely on the React UI to hide sensitive fields. Likewise, command/office metadata shown to players must not expose staff/admin command names, moderation command descriptions, or raw office permission strings such as `legislative_leader`.
- **API list envelopes are `{ data, total }`.** Web hooks expect this shape for players, bills, documents, tickets, voting, favours, and moderation. Routes should translate legacy parameter aliases (`party`/`partyId`, `page`/`offset`, etc.) at the edge, then pass normalized filters into services. Document routes must stay mounted from `buildApp`, and document diff responses are structured `{ from, to, hunks, stats }` objects consumed directly by web redline views. The web API client treats a 2xx non-JSON response as a configuration error, which catches “served the SPA HTML instead of API JSON” deploy mistakes.
- **DB schema rollouts need both migration coverage and narrow reads.** Drizzle schema edits are not enough: when adding or renaming columns, add/extend an idempotent migration or one-shot script that covers every column/table the deployed code will read or write, then run its dry-run/output check and add a regression test for that migration contract. Before deploying code that touches a changed table, search for full-row `.select()` / `.returning()` on that table and narrow any path that only renders a subset of fields, especially Discord bot commands. A generic bot "database error" right after a schema-related deploy should be treated as likely schema drift (`column does not exist`, `NOT NULL`, missing table) until logs prove otherwise.
- **Bill API responses include display player summaries.** `billService` enriches bills with nested `author`, `submittedBy`, and `coSponsors` summaries in addition to `authorId`, `submittedById`, and `coSponsorIds`; the web bills list/detail views render those nested summaries, so do not drop them when touching bill mappers or list endpoints.
- **Bills can be Google Doc or short text sources.** `bills.bill_type` is `'google_doc' | 'short'`; short bills store their authoritative text in `cached_content` and have `google_doc_url` / `google_doc_id` set to null. `/bill submit` first asks the player to pick Google Doc vs Short Bill, then opens the matching modal. `/bill view` paginates short-bill text into Discord-safe embed descriptions. `/bill edit field:text` updates `cached_content`/`cached_at` for short bills only; Google Doc bills must be edited in the document and refreshed with `/bill recache`. Existing DBs need `pnpm --filter @hansard/db migrate:short-bills` or an equivalent schema push before deploying this code; that migration must cover `bill_type`, nullable `google_doc_url`, `google_doc_id`, `cached_content`, and `cached_at`.
- **`migrate:short-bills` must backfill legacy Google Doc IDs.** Pre-short-bill databases may already have populated `google_doc_url` rows; the migration script needs to extract `google_doc_id` from those URLs when the new column is null, or later recache/fetch paths that require `googleDocId` will strand old bills.
- **Legislative vote creation posts the bill source.** The `/vote create type:legislative_vote` public vote message attaches the linked Google Doc URL or paginated short-bill text immediately when the vote is opened, so voters can read the bill before reacting/casting. Keep that source lookup narrow (`googleDocUrl` + `cachedContent`) rather than selecting `billType`, because the legislative vote path is designed to tolerate older deployments that have not run `migrate:short-bills`.
- **Office holder identity is flat on `/api/offices`.** `listOffices()` / `getOffice()` attach `playerName` and `discordUsername` directly to each `currentHolders`/`holderHistory` row rather than nesting a `player` object. Web office views should render those flat fields, or normalize them before passing holder data into shared player UI.
- **Player voting records are privacy-aware.** `getPlayerVotingRecord(db, playerId, viewer)` must receive the session player context from routes. It may return `choice: null` and `castAt: null` for anonymous ballots, sealed in-progress elections, or records the viewer cannot inspect. The web dossier renders those nullable fields as `Private`; do not reintroduce raw ballot choices into public player views.
- **Dead characters do not cast counted votes.** `VoteService.getEligibility` rejects `players.isAlive=false`, and `VoteService.tallyVotes` joins ballots to `players` so only voters still alive at tally time count. Reaction-mode voting must mirror this guard before writing mutable reaction ballots, and `/vote eligibility` should report the same reason string rather than diverging from service rules.
- **Character reincarnation reuses the same player row.** When a dead character is replaced, `/character create` and staff character creation archive the old character into `profileData.previousCharacters`, reset the current character/lifecycle fields on the same `players.id`, and log `reincarnation`. Current-state commands should read the new character from `players`, but must filter current-only joins such as offices with `office_holders.end_date IS NULL`. Active phone numbers intentionally inherit because they are player/account assets keyed by `phone_numbers.player_id`; directory and call flows should show the successor's current character name for inherited lines.
- **Election turnout and simulation history are privacy-aware.** `VoteService.getTurnout(id, viewer)` must receive the session player context from routes and hide live turnout from non-staff viewers when `config.sealedResults` or `config.anonymousBallots` is set. Bot turnout commands should mirror that rule. `sanitizeTimeAdvanceLog(row, viewer)` redacts per-player simulation summary IDs and staff notes for non-staff history consumers; do not expose raw `time_advance_log.notes` outside staff views.
- **Production cookie/proxy setup** — Web and API are served same-origin in production: nginx in `Dockerfile.web` (config template at `packages/web/nginx.conf.template`) reverse-proxies `/api/*` to the API service via the `API_UPSTREAM` runtime env (e.g. `http://${{api.RAILWAY_PRIVATE_DOMAIN}}:3001` on Railway). The web image's `VITE_API_URL` build arg defaults to `/api` so the React app fetches on its own origin. **`DISCORD_REDIRECT_URI` must point to the web origin too** (e.g. `https://hansard.example/api/auth/discord/callback`, not the API host), and the Discord Developer Portal "Redirects" allowlist must include that exact URL — otherwise OAuth fails with `invalid_redirect_uri`. Same-origin removes the cross-site cookie classification that Brave and stricter browser modes were dropping after the Discord OAuth callback (which manifested as a successful Discord auth that then redirected back to `/login`); a previous `sameSite: 'none'` cross-subdomain config worked in default Chrome/Firefox but not in browsers that block third-party cookies. Session cookies are now `sameSite: 'lax'` + `secure: true` in production, `sameSite: 'lax'` + `secure: false` in dev. Fastify is still constructed with `trustProxy: true` so `request.protocol` honours `X-Forwarded-Proto`; nginx must forward Railway's `X-Forwarded-Proto: https` rather than overwriting it with its own `$scheme` (which is `http` after TLS terminates at Railway's edge) — `nginx.conf.template` uses `$forwarded_proto` (a `map` of `$http_x_forwarded_proto` falling back to `$scheme`) for this. Without this chain, `@fastify/session` sees a non-https connection and silently refuses to persist a `secure: true` cookie, reproducing the original Brave bug under a new mask. If the API service is also exposed on a public domain, do not log in via that domain — its cookies live on a different origin from the web app's and won't be sent on `/api/*` requests through the proxy; consider unpublishing the API's public Railway domain to prevent confusion. **The web nginx must re-resolve the upstream hostname at runtime, not cache the boot-time IP.** Railway rotates `api.railway.internal`'s internal IP on every API redeploy, so a `proxy_pass http://api.railway.internal:3001;` with a literal hostname pins the dead IP and the web container 504s until itself redeployed. `nginx.conf.template` resolves this with `resolver ${NGINX_LOCAL_RESOLVERS} valid=10s;` (the env var is populated from `/etc/resolv.conf` by the nginx:alpine image's `/docker-entrypoint.d/15-local-resolvers.envsh` and is in `Dockerfile.web`'s `NGINX_ENVSUBST_FILTER` allowlist) plus `set $api_upstream ${API_UPSTREAM}; proxy_pass $api_upstream$request_uri;` — variable-form `proxy_pass` is what actually defers resolution to per-request, the literal form is parsed once at config load. **`15-local-resolvers.envsh` is opt-in via `NGINX_ENTRYPOINT_LOCAL_RESOLVERS=1`** — without that env var set in `Dockerfile.web`, the script `return 0`s without exporting `NGINX_LOCAL_RESOLVERS`, then envsubst can't substitute it (the filter only matches names actually present in the environment), the literal text `${NGINX_LOCAL_RESOLVERS}` survives into the rendered conf, and nginx hard-crashes at boot with `[emerg] host not found in resolver "${NGINX_LOCAL_RESOLVERS}"` on a tight restart loop.
- **Web sessions are Postgres-backed.** `@fastify/session` is wired to a `DrizzleSessionStore` (`packages/api/src/sessionStore.ts`) keyed on the `sessions` table — *not* the library default in-memory store, which drops every session whenever the API process recycles. On Railway under `tsx watch` that recycle is frequent enough to log every web user out every few minutes. `dbPlugin` is registered before the session plugin in `buildApp` so `fastify.db` exists when the store is constructed. The plugin's rolling-cookie behaviour rewrites the 7-day expiry on every authenticated request, so active users get a sliding window; lapsed rows are cleaned up lazily on read (no background sweeper). Roll out the column/table with `pnpm --filter @hansard/db migrate:sessions-table` before deploying code that reads it.
- **MCP server is read-only and reads DB directly.** `@hansard/mcp` opens its own Postgres pool and calls API service functions directly (re-exported via `@hansard/api/services/*`). The API is the *auth oracle only* — the CLI obtains a long-lived bearer via a Discord-OAuth-backed device flow (`/api/auth/device/*`), then `/api/auth/mcp/me` refreshes identity + permissions every 5 minutes. Tokens are sha-256 hashed at rest with dual expiry (90-day sliding + 1-year absolute). Read tools mirror what `requireAuth`-only API routes already expose; **the API has no per-permission read filtering**, so MCP tools introduce no new authorization surface — but `permissions.ts` was deliberately removed and must be reintroduced before exposing any v2 mutation tools. Ticket MCP reads must go through `TicketService` with `{ userId, isStaff }` viewer context so non-staff visibility stays aligned with `/ticket list` and `/ticket view`. Set `PUBLIC_API_URL` in production so device-flow URLs don't trust the `Host` header (which `trustProxy: true` reflects).
- **MCP ticket detail uses `get_ticket`.** `packages/mcp/src/tools/tickets.ts` exposes `list_tickets` for summaries and `get_ticket` for a single ticket by UUID or human ticket number. `get_ticket` must keep delegating to `TicketService.getTicket` / `getTicketByNumber` with the MCP session viewer context so replies, internal notes, and audit history obey the same staff/non-staff visibility policy as the API and bot.
- **MCP favour audit uses `get_favour_transaction_ledger`.** The staff-only MCP ledger tool reads `favour_transactions` through `getAllHistory` and supports filters for player, category, transaction type, grantor, limit, and offset. Use it to prove historical favour grants/spends/removals directly; do not reconstruct global favour history from balances or ticket text when the authenticated MCP session is staff.
- **Aging is computed live from `birthDate` against the simulation clock.** `players.birthDate` is the source of truth — `currentAge` is a denormalized integer cache, refreshed each `advanceTime` and on character creation. Date math + age computation lives in `@hansard/shared/utils/aging.ts` (`parseSimDate`, `calculateAge`, `birthDateForAge`, `advanceDateByTicks`). If the clock row is missing or a caller passes an unparseable date, character birth dates fall back to `DEFAULT_SIMULATION_CURRENT_DATE` (`2075-01-01`) rather than wall-clock time. Both ISO (`YYYY-MM-DD`) and freeform (`Year X, Month Y`) formats are supported, but freeform sim dates **reject** day/week ticks — `advanceDateByTicks` throws because freeform has month resolution. Multi-tick advances loop the ailment + death roll **per tick** so `/time advance ticks:5` is statistically equivalent to five sequential 1-tick calls. Automatic death rolls now create `profileData.pendingDeath` plus a `death_pending` event and leave the character alive/officed until the next `advanceTime`, which finalizes the death before rolling that player again; manual staff deaths still happen immediately. Pending deaths store an ailment snapshot (`condition` + `severity`) so the eventual death details, event log, bot `/time` messages, and web preview rows list all active ailments that were present when the roll triggered; manual `/character kill` obituaries do the same from the character's current ailments. Aging knobs (thresholds, ailment pool, scaling) live in `simulation_clock.aging_config` (JSONB, nullable); `getAgingConfig(db)` falls back to `DEFAULT_AGING_CONFIG` exported from `simulationService.ts`. The default automatic ailment pool is intentionally normal-but-dangerous for the 2075 setting: no minor or ordinary curable conditions, only major/critical ailments such as cancer, organ disease, stroke, embolism, sepsis, and failure states. The bot's `/time advance` and `/time preview` delegate straight to `advanceTime` / `previewAdvance` from `@hansard/api/services/simulationService` — no inline duplication. Because of this cross-package import, `Dockerfile.bot` ships `packages/api/` (its `package.json` at install time, source tree at copy time) even though the bot doesn't run the Fastify server — `simulationService.ts` only pulls `drizzle-orm` + `@hansard/db` + `@hansard/shared`, so no fastify-side runtime cost. The whole pipeline (per-player updates, ailment events, pending death/death + office vacancy, clock tick, time-advance log) runs in a single `db.transaction` so a partially-applied advance can never strand the world.
- **Production runs `tsx watch` via Dockerfiles, not compiled output.** Both `Dockerfile.api` and `Dockerfile.bot` end with `CMD ["pnpm", "dev:api"]` / `["pnpm", "dev:bot"]` — i.e., `tsx watch src/index.ts`. We do **not** run `node dist/index.js` in production. Reason: `tsconfig.base.json` uses `moduleResolution: "bundler"`, so `tsc` emits relative imports without `.js` extensions (`import './schema'`), which Node ESM rejects with `ERR_UNSUPPORTED_DIR_IMPORT`. Workspace `package.json` `exports` maps point straight at `./src/index.ts` for the same reason. Anyone re-attempting a "real" build pipeline must first migrate `moduleResolution` to `nodenext` and add `.js` extensions to every relative import across `db`/`shared`/`api`/`bot`/`mcp`. Don't add `--conditions=development` to `tsx watch` — tsx requires `watch` as the first positional arg, so `tsx --conditions=X watch ...` parses `watch` as the entry file and crashes with `ERR_MODULE_NOT_FOUND`.
- **Bot command modules are imported from filesystem paths.** `packages/bot/src/commandLoader.ts` converts every discovered command path through `pathToFileURL(...).href` before dynamic `import(...)`; raw Windows paths (`C:\...`) crash Node's ESM loader with `ERR_UNSUPPORTED_ESM_URL_SCHEME`. Runtime command discovery also excludes `*.test.ts` / `*.spec.ts` so Vitest suites are never imported during bot startup. Helper modules without `default.data.name` may still be discovered and skipped with a warning.
- **Discord interaction collectors must not race the global handler, but must also recover from stale tokens.** When a command uses `awaitModalSubmit` / `awaitMessageComponent`, the same interaction also reaches the client-level `InteractionCreate` listener in `events/interactionCreate.ts`. If the global handler calls `interaction.reply(...)` for an in-flight collector-managed customId, it consumes the response token and the awaiter's `deferReply()` fails with `DiscordAPIError[10062] Unknown interaction`. But if the global handler stays *silent* on a collector-managed customId whose awaiter has already timed out, Discord paints "Something went wrong" on the user's screen because nothing acknowledged the submission within 3 seconds. Both failure modes are solved by the `packages/bot/src/utils/awaitingInteractions.ts` registry: commands wrap their `awaitModalSubmit` / `awaitMessageComponent` in `registerAwaitingInteraction(customId)` / `unregisterAwaitingInteraction(customId)` (use `try/finally`), and the global handler treats collector-managed customIds NOT in the registry as stale and acks them with a friendly "session expired" message. New awaited customIds must still be added to `COLLECTOR_MANAGED_PREFIXES` so the global handler can recognize them, and must call the register/unregister helpers around the await so the in-flight case is preserved. Awaiter timeouts should match Discord's 15-minute interaction-token lifetime (use `840_000` ms = 14 min) — shorter timeouts let Discord-valid submissions reach the global handler as "stale", which works correctly but is a worse user experience than letting the awaiter handle them.
- **Modal submits should be acknowledged before DB/network work.** Discord paints a client-side "Something went wrong" banner if a modal submit is not acknowledged quickly enough, even if the command keeps processing and eventually writes the database. For multi-step flows like `/character create`, call `modalSubmit.deferReply({ ephemeral: true })` immediately after `awaitModalSubmit`, then use `editReply` for validation errors and later prompts.
- **Phone PR #9 review hardening.** `/phone` is the only globally registered command; all other slash commands are guild-scoped and each guild is swept with the full command set. `PhoneService` serializes number/player mutations with transaction-scoped advisory locks, rejects expired rings at answer/decline time, and orders tap failure streaks by `phone_message_tap_deliveries.created_at`. Tap delivery validates both per-tap channels and `PHONE_TAP_CHANNEL_ID`, requires `mirror-user` targets to be staff, preserves staff/tap audit even when the recipient DM fails, and `migrate:phones -- --validate` validates the deferred constraints after cleanup. **Staff force-end persists the actor uuid on `phone_calls.force_ended_by_id`** (audit column, not just `ended_reason` parsing) — `/phone admin force-end` resolves the invoking Discord snowflake to the player row and passes that UUID. **`recordMessage` runs inside `db.transaction` with `SELECT … FOR UPDATE` on the call row and sender player row** so a concurrent `endCall` or death finalization cannot leak a message into a transcript whose call/player state has already changed. **Retired numbers can be re-registered** (by anyone, including the original owner) — uniqueness lives on a partial unique index `phone_numbers_active_normalized_unique WHERE is_active = true` rather than a column-level UNIQUE, so `deactivateNumber` doesn't permanently burn the digits. **Recipient hangup on a still-ringing call writes `(status=declined, endedReason=declined_by_recipient)`** — the same audit pair as the Decline button, so the entry point doesn't change the trail. The slash-option `reason` for `/phone admin force-end` is preserved up to 59 chars in `ended_reason` (was unnecessarily sliced to 48). **`ensureStaff` / `discordUserIsStaff` require both `players.isStaff` and a live configured staff role, and honour `PHONE_GUILD_ID`** — when set, staff-role membership is checked against that guild only, so stale DB flags or unrelated-guild roles do not grant phone admin powers. Tap delivery **re-checks `tap.isActive` via `PhoneService.isTapActive`** immediately before posting each per-tap copy so a concurrent revoke between the active-tap snapshot and the fan-out does not produce a final mirror to the now-revoked destination. The `ensurePhoneThread` staff-add fan-out (`Guild.members.fetch()` + per-member `thread.members.add`) **runs in the background** via `void backgroundStaffAdd(...)` so the first relayed message of a brand-new pair doesn't pay the multi-second fetch cost. All user-content DM relays and call-state DMs pass `allowedMentions: { parse: [] }`; `message.reply(...)` hints in `messageCreate.ts` pass `allowedMentions: { repliedUser: false, parse: [] }` so the bot does not ping the player it's already DMing.
- **Phone calls are a frozen, fully-mirrored ledger.** `/phone register` lets a player claim a self-chosen number (normalized to digits with optional leading `+`, 3-20 chars; DB-level `CHECK (number_normalized ~ '^\+?[0-9]{3,20}$')` backstops the app-side regex against Unicode look-alikes); `/phone directory` lists active `phone_numbers` joined to alive players with real `characterName`s via `PhoneService.listDirectory` (paged/searchable, `allowedMentions: { parse: [] }`); `/phone dial` opens a session-based `phone_calls` row, DMs the recipient a ring with Answer/Decline buttons (60s `ring_expires_at`, ring DM id persisted via `PhoneService.setRingMessageId` so terminal transitions disable stale buttons), and routes subsequent DM lines through `events/messageCreate.ts` into `PhoneService.recordMessage` plus `utils/phoneRelay.ts`. **No Discord-side edits/deletes are propagated** — the ledger is the audit copy. The bot needs `GatewayIntentBits.DirectMessages` to receive DMs (already enabled). `messageCreate.ts` does **not** filter `/`-prefixed content — in DM channels Discord delivers real slash commands as interactions, so any `/` line here is just text the player typed and must be relayed/frozen. **Slash commands MUST be registered globally** (`application.commands.set`) for `.setContexts(...BotDM)` to be honored — Discord ignores the contexts array on guild-scoped commands, so a `guild.commands.set(...)` registration silently breaks every DM-context feature (notably `/phone hangup` from a call DM). `events/ready.ts` registers globally by default and optionally clones to a `DEV_GUILD_ID` for instant-update dev iteration. Rollout requires `pnpm --filter @hansard/db migrate:phones` before deploy; the script wraps every statement in a single `sql.begin(...)` transaction so a partial failure rolls back, adds CHECK constraints with `NOT VALID` (no full-table lock on add, and pre-migration violators don't abort the migration — operator runs `VALIDATE CONSTRAINT` after cleanup), creates seven tables including partial unique indexes (`phone_calls_one_open_caller/recipient WHERE status IN ('ringing','active')`, `phone_calls_active_started_idx WHERE status='active'` for the stranded-call sweep), and renames legacy `mirror_user_id` → `mirror_discord_user_id` idempotently across both `phone_taps` and `phone_tap_audit_log` (including the "both columns exist" merge case). Service mutations catch `23505` and surface `PHONE_ALREADY_ON_CALL` / `PHONE_NUMBER_TAKEN`. Dead characters cannot place, receive, **answer, decline, OR send a message mid-call** — the messageCreate relay catches a `dead` error from `recordMessage` and `systemEndCall`s the call as `session_reset` so the counterparty isn't left typing into a one-way pipe. `deactivateNumber` refuses if the line is on an open call. `PhoneService.endCall(callId, actorId)` is **actor-derived** — the reason (`cancelled_by_caller` / `hangup_caller` / `hangup_recipient`) is computed from the call's status and the actor's role; callers cannot spoof a counterparty hangup. System teardowns go through `systemEndCall(callId, reason)` (`ring_timeout` / `dm_closed` / `relay_failed` / `session_reset` / `number_deactivated`). `findOpenCallForPlayer` issues two sequential single-column lookups (one per role) instead of `WHERE caller=X OR recipient=X` so each lookup hits its partial unique index instead of a planner-fragile `BitmapOr`. Every call gets a per-unordered-pair private thread under `PHONE_LOG_CHANNEL_ID`, reused across sessions; thread creation is **mutexed per pair in-memory** in `phoneRelay.ts` so two concurrent first-messages don't race and orphan a Discord thread, **replaces stale persisted Discord thread rows after a failed fetch**, uses the fetched log channel's `guild` for staff role pings, and is opened immediately on Answer (not lazily on the first relayed message) so zero-message calls still produce a staff audit thread. Staff role resolution lives in the shared `utils/staffRoles.ts` (`resolveStaffRoleIds`) used by both `sendTicketStaffPing` and the phone log opener — `STAFF_ROLE_IDS` / `STAFF_ROLE_ID` / fallback to a role named `Staff`. On phone-thread creation the bot follows the ping with `thread.members.add(...)` for each resolved staff member (5-at-a-time concurrency cap) so staff are actually present, not just notified. Staff-set `/phone admin tap-create` writes a `phone_taps` row plus a denormalized `phone_tap_audit_log` snapshot (target number, mirror channel/user copied at action time) **inside a single `db.transaction` after locking and re-checking the target number** so a rogue staff member can't tap-and-untap silently or race a number retirement; `setTap` refuses taps with no destination (`mirror-channel` / `mirror-user` / `PHONE_TAP_CHANNEL_ID` all empty); `/phone admin tap-create` rejects mirror channels where the effective `@everyone` permission (per `channel.permissionsFor(everyone)` — honors category inheritance) includes `ViewChannel`, refuses public threads even under a private parent, refuses announcement channels, and validates the parent for private threads (a thread under a public parent inherits its visibility); and the slash option is locked at the UI to `GuildText | PrivateThread` via `addChannelTypes(...)`. Multi-line content is chunked across Discord-safe messages — 1900 chars per DM, 4000 per embed — never silently truncated; the persisted `phone_messages.content` always has the full content, and the sender sees a 📨 reaction on any DM over 1900 chars so they know the recipient saw a split message. DM-context features require both `.setContexts(Guild, BotDM)` on the slash command **and** global registration; `ensureStaff` performs a Discord-id-based player lookup when `interaction.member` is null and still requires a live configured staff role, so a stale `players.isStaff` flag alone cannot authorize DM admin actions. On `ClientReady` the bot warns if it's in multiple guilds without `PHONE_GUILD_ID` set, and separately warns if `PHONE_LOG_CHANNEL_ID` resolves to a channel where `@everyone` has effective `ViewChannel` (phone log thread names would leak). - **Phone voicemail is caller-only after the peep.** `/phone voicemail set number:<owned> intro:<text> after-peep:<text>` stores two per-number messages; `PhoneService.initiateCall` snapshots them onto the `phone_calls` row so later edits do not rewrite in-flight calls. The intro is DM'd to the caller immediately, deliberately without labeling it voicemail, but it still goes through `recordVoicemailPrompt` + `relayMessage` so staff threads and taps see the same ledger content as the caller. Voicemail leaves only the caller in an open-call state (`phone_calls_one_open_caller WHERE status IN ('ringing','active','voicemail')`; recipient open-call checks remain `ringing|active`). Ring-DM terminal notices that say the caller was sent to voicemail must include the caller's public line label (`numberRaw` or pseudonym + number) so the mailbox owner can tell which number called. Do not treat `voicemail` as a live two-party call: recipients can place/receive calls while someone is leaving them a voicemail.
- **Default phone voicemail is opt-out.** New `/phone register` rows set `voicemail_enabled=true` and store the standard messages from `PHONE_DEFAULT_VOICEMAIL_INTRO_MESSAGE` / `PHONE_DEFAULT_VOICEMAIL_POST_BEEP_MESSAGE`; `/phone voicemail set` customizes them and `/phone voicemail disable` is the explicit opt-out. `migrate:phones` also sets the DB defaults and backfills active existing `phone_numbers` with default messages, while leaving historic `phone_calls` snapshots alone.
- **Phone log backfill is staff-tool, not infrastructure.** `phone_calls.backfilled_at` is the completion idempotency marker for the one-shot `pnpm --filter @hansard/bot backfill:phone-threads` script (added 2026-05-15 for the initial PHONE_LOG_CHANNEL_ID rollout). Run the migration `pnpm --filter @hansard/db migrate:phone-backfill-marker` (supports `--dry-run` and `--validate`) before deploying code that reads `backfilled_at`. The script supports `--dry-run`, `--limit N`, `--verbose`, and serializes on a `pg_advisory_lock(1504812456)`; dry-run does a non-blocking `pg_try_advisory_lock` and warns if another run holds it. Per-thread pacing is 1100ms to respect Discord's 5/5s per-channel rate limit; the outer loop is serial. Live calls (`status IN ('ringing','active')`) are skipped by filter; pair-shared threads created by the live relay are reused without re-pinging staff.

## Bot Persistence Patterns

- **Vote/election writes are direct DB for election creation, but ballot casting uses API service rules.** `/vote create` modal handler and `/vote elect` write elections directly via `db.insert(elections)`. The legislative bill vote helper and bot bill list/submit acknowledgement paths intentionally use narrow `bills` projections/returning payloads so older deployments that have not yet run `migrate:short-bills` do not fail on missing newly-added bill columns; do not replace those paths with full-row `select()` / `returning()` unless the rollout dependency is deliberate. The `vote-confirm:*` button handler constructs the method-specific ballot payload, then calls `VoteService.castBallot` so Discord votes reuse the same eligibility, ballot-format, candidate-registration, and duplicate-vote checks as the API.
- **`/vote schedule` is not a bill-vote path.** Scheduled legislative votes must be rejected and redirected to `/vote create type:legislative_vote`, because only the create flow links `relatedBillId`, advances the bill to `voting`, and records the corresponding `bill_status_log` entry.
- **Bill vote cancellation is an audited recovery, not a delete.** `/vote cancel` uses `voting.cancel` (aliased to `legislative_leader`) and `/bill reraise` uses `voting.create`; both refuse certified elections, mark the old election `cancelled`, reset linked legislative bills to `submitted`, clear `playerVoteId`/`playerVoteResult`/`playerVoteAt`, and append a `bill_status_log` entry with the optional reason. Keep the conditional `WHERE` guards on election status, bill status, and `playerVoteId` so stale cancellations cannot reset a bill after another workflow moved it. Ballots remain attached to the cancelled election for audit history.
- **Bill withdrawal is an audited status transition.** `/bill withdraw` lets the bill author or original submitter withdraw only `submitted` bills; it sets status to `withdrawn` and writes a `bill_status_log` row with the optional reason. Do not delete withdrawn bills or reset linked vote fields in this path - once a bill has reached `voting` or later, use `/vote cancel` or `/bill reraise` for recovery.
- **Default vote duration is shared.** Newly-created votes, scheduled votes without `duration-hours`, legislative bill vote helpers, position-election voting windows, and runoff rounds use `DEFAULT_VOTE_DURATION_HOURS` / `DEFAULT_VOTE_DURATION_MS` from `@hansard/shared/constants/config.ts`. Keep new vote creation paths on that shared 24-hour default instead of hardcoding 24, 48, or 7-day windows.
- **Overdue vote closing is automatic.** The bot starts `startVoteAutoCloseWorker` on `ClientReady`, scans `voting_open` elections whose `votingClosesAt <= now` every minute, marks them `voting_closed`, and reuses the reaction result renderer for reaction-mode embeds. The catch-up script is `pnpm --filter @hansard/bot close:due-votes` with `--dry-run` and optional `--render-discord`. Ballot paths still enforce `votingClosesAt` defensively, so overdue votes reject new API/button and reaction ballots even if the worker has not ticked yet.
- **Closing a legislative vote also tallies it and fully auto-enacts it when allowed.** `/vote close` and the auto-close worker both call `VoteService.tallyVotes` for `legislative_vote` elections with a `relatedBillId`, so the linked bill transitions out of `voting` without a separate `/vote tally` step. `VoteService` itself only records the player-house outcome: passed linked bills move to `player_passed` when the NPC house is inactive, `npc_pending` when the NPC house is active, and `player_rejected` when rejected. Discord-capable bot paths (`/vote close`, `/vote tally`, and the live auto-close worker) must then call `autoEnactPassedBillFromElection` for passed inactive-NPC bills so `/bill enact`'s full side effects happen automatically: status becomes `enacted`, `enactedAt`/`effectiveAt` are set, the legislation channel embed is posted, and `legislation_channel_id`/`legislation_message_id` are captured. Do not reintroduce API-service-only enactment, because the API service cannot post to Discord and would create ghost laws with no ordinance message. Other election types still rely on manual `/vote tally`. Tally failures are non-fatal — the election stays `voting_closed` and staff can re-run `/vote tally`.
- **Certification requires a tallied election.** `VoteService.certifyElection` and `/vote certify` both reject elections whose status is not `tallied` (or `npc_pending` when NPC confirmation is required). Without this guard, certifying a `voting_closed` election bypasses `updateRelatedBillAfterTally` entirely — bills stay in `voting`, position elections never appoint, and `results` remains null. If you need to recover an already-certified election with null results, backfill `elections.results` JSONB and run `updateRelatedBillAfterTally`'s effects manually rather than weakening the guard.
- **Bill votes respect the season NPC-house toggle.** `simulation_clock.npc_house_active` defaults false and is staff-toggleable via `/time npc-house active:<true|false>`. Roll out the column with `pnpm --filter @hansard/db migrate:npc-house-active` before deploying bot/API code that reads it. When `VoteService.tallyVotes` tallies a linked `legislative_vote`, passed bills become `player_passed` with `npcVoteRequired=false` while the NPC house is inactive; the bot layer immediately auto-enacts that `player_passed` bill through `autoEnactPassedBillFromElection` when a Discord client is available. If the toggle is active, passed bills become `npc_pending` with a pending `npcVote` and are not enacted until NPC review passes. Rejected linked bill votes become `player_rejected`. Keep this under `/time` rather than a new top-level command because the bot is at Discord's 100-command surface cap.
- **Ticket reads in the bot must use `TicketService` visibility.** `/ticket list` and `/ticket view` resolve a `TicketAccessContext` via `getTicketViewer`; non-staff users only see tickets they created or are assigned to. `assignedToId` is a player UUID, not a Discord snowflake, so mention rendering must resolve `players.discordId`. `/ticket history` renders a full timeline from `ticketMessages` plus staff-visible `ticketAuditLog`; keep its audit action renderers in sync with service-written actions such as `linked` and `unlinked` so persisted audit rows do not vanish from Discord history. `/ticket assign` must validate the selected guild member is staff before mutating the ticket or adding them to a private thread. `TicketService.assignTicket` enforces the same rule server-side — it looks up the target `players.isStaff` and throws `TicketAssigneeNotStaffError` (translated to HTTP 400 by `/api/tickets/:id/assign`) before any update, because assigning to a non-staff player would otherwise grant that player ticket visibility via the `assignedToId === user.id` branch in `getTicket`/`listTickets`.
- **Ticket reopening restores open lifecycle state.** `/ticket reopen` follows the same creator-or-staff authorization model as `/ticket close`, moves only closed tickets back to `open`, clears both `closedAt` and `resolvedAt`, writes a `reopened` audit row, and optionally records a public `**Reopened:** ...` reason message. Its Discord thread updates are best-effort: unarchive, unlock, then post a reopen embed with `allowedMentions: { parse: [] }`.
- **Ticket owner notifications are best-effort.** `/ticket reply` persists the public `ticket_messages` row first, then DMs the ticket creator when someone else replies. Resolve the creator through `tickets.createdById -> players.discordId`, skip self-notifications, and swallow/log DM lookup or send failures so Discord notification issues never make a saved ticket reply look failed.
- **Ticket Discord thread IDs are trusted routing state.** `tickets.discordThreadId` controls where internal notes and staff updates are mirrored, so player-facing API update paths must treat it as staff-only and pass sanitized `UpdateTicketData` objects into `TicketService`. Do not forward raw request bodies into ticket mutations; a creator must not be able to repoint the mirror target before staff add private notes.
- **Ticket descriptions should stay readable in full.** The web Tickets list renders each ticket's `description` beneath the title with preserved line breaks, and Discord ticket summary/view embeds pass through the stored description without arbitrary local slicing. When Discord hard limits apply, use explicit pagination: `/ticket view` uses `createPaginatedEmbed` with ticket action rows preserved, pinned summaries split across multiple embeds up to Discord's per-message embed cap, and ticket opening text is sent as multiple Discord-safe messages.
- **Discord channel env vars are bot-service runtime config.** `TICKET_CHANNEL_ID` enables `/ticket create` private thread creation in the staff ticket channel. `GAME_EVENTS_CHANNEL_ID` overrides the SCORP3 game-events default (`1503483556914266254`) used by `packages/bot/src/utils/gameEventsChannel.ts`; `/time advance` posts a public best-effort time summary there while keeping pending death rolls only in the staff reply, and the legacy `ANNOUNCEMENT_CHANNEL_ID` env var remains a fallback. `MOD_LOG_CHANNEL_ID` enables best-effort moderation log posts from state-changing `/mod` commands; missing or failed modlog sends must never roll back the persisted moderation action. `GRAVEYARD_CHANNEL_ID` overrides the SCORP3 graveyard default (`1499836838192480488`) used by `packages/bot/src/utils/graveyard.ts`; both manual `/character kill` and finalized automatic deaths from `/time advance` post best-effort obituary embeds through that shared helper, and failed sends must not roll back death persistence. `LEGISLATION_CHANNEL_ID` overrides the SCORP3 legislation/laws default (`1499837130254581854`) used by `packages/bot/src/utils/legislationChannel.ts`; amendment submissions and `/bill repeal` post best-effort legislation embeds there, but `/bill enact` (from `submitted`, `player_passed`, or `npc_passed`) and auto-enactment are message-first: they must successfully create a legislation-channel post and capture its message id before flipping the bill to `enacted`, with the status change and `bills.legislation_channel_id`/`bills.legislation_message_id` stored together in the enactment transaction. This prevents ghost laws where the DB says enacted but the ordinance channel has no law post. Keep `voting` out of `/bill enact` unless linked-election cleanup is handled, because a later tally can otherwise overwrite the direct enactment. `/bill enact` may repair an already-`enacted`/`active` bill only when those stored legislation-message fields are missing, by posting the missing enactment embed and persisting the IDs without adding another status transition. `/bill repeal` can then edit the original embed in place — repealed laws keep their slot in the channel scrollback with a 🚫 [REPEALED] title prefix and a strikethrough enactment line, instead of duplicating an announcement. Roll out the columns with `pnpm --filter @hansard/db migrate:bill-legislation-message` before deploying code that reads them. Legacy enacted bills (and any post where the original message id was never captured) fall back to a fresh `Bill Repealed` notice via `postLegislationEmbed`; stored-message edit failures such as `message_missing`, `not_sendable`, and `failed` should be reported as edit failures in the staff reply, even if the command also posts a fresh fallback notice. Failed channel writes log but must not roll back the persisted repeal — the DB transaction is the source of truth. Keep deployment-specific channel values on the Railway `bot` service, not in committed env files. Web/API-originated ticket thread mirrors are the exception: the API service needs `TICKET_THREAD_MIRROR_BOT_TOKEN` (or shared `DISCORD_BOT_TOKEN`) so `TicketService` can post best-effort updates to existing Discord ticket threads.
- **Message export is on-demand, staff-only, and allowlisted.** `/api/messages/export` fetches recent Discord messages through the REST API with `DISCORD_BOT_TOKEN` and only from `MESSAGE_EXPORT_CHANNEL_IDS`; allowlisted parent channels also expand to accessible active and archived threads beneath them. It is an LLM-ingestion export, not a general chat archive, and ordinary server chat is not stored in Postgres by this feature. Keep sensitive/private channels out of the allowlist unless staff explicitly want them exported.
- **Ticket thread messages are staff-only and best-effort.** After `/ticket create` opens a private thread, the bot does not add the ticket creator to that thread; it posts staff-role pings, the ticket summary/actions, and the opener text for staff review. Resolve comma/space-separated `STAFF_ROLE_IDS` first, include legacy `STAFF_ROLE_ID` if present, and fall back to a guild role named `Staff`; missing or failed pings/messages must not roll back ticket persistence or thread creation. Web/API-originated mirrors must suppress Discord mentions (`allowed_mentions.parse = []`) because ticket bodies are user-controlled but sent through the bot token. The bot `/ticket create` path mirrors that rule: `sendTicketSummaryMessage` (summary embeds carrying the creator's title/description) and `sendOpeningTicketMessage` (opener echoing the description) both pass `allowedMentions: { parse: [] }` so a creator cannot `@everyone` or ping staff roles through the bot. The staff-ping send in `sendTicketStaffPing` is the only path that intentionally pings roles and stays unchanged.
- **Ticket categories are seeded from the bot.** `/ticket category-create` is staff-only and writes active `ticket_categories` rows directly with Drizzle; keep the parent `/ticket` command visible at the Discord definition level and rely on the runtime `isStaff` check so staff roles without Discord `Manage Guild` can still find it. `/ticket categories` lists active rows in `sortOrder`/name order. The user-facing `/ticket create` flow still depends on at least one active category before it can open the select menu.
- **Command loading is centralized.** Startup calls `loadCommands` from `packages/bot/src/commandLoader.ts`; keep recursive loading, `*.test.ts` filtering, URL-based dynamic imports, and duplicate slash-command detection there instead of reintroducing inline loader logic in `src/index.ts`.
- **Keep guild slash commands under Discord's 100-command cap.** `commandLoader.test.ts` loads the real command tree and fails if `commands.size > 100`; prefer grouping new actions under existing command namespaces. The standalone `time-pause`, `time-preview`, `time-set`, `time-unpause`, and `time-history` commands were retired because `/time pause|preview|set|unpause|history` already cover those paths.
- **Roster lines should expose the Discord-account mapping.** `/player roster` already selects `players.discordId`; render it as `<@${discordId}>` beside the character name so staff and players can see which Discord account owns each character without running `/player whois`.
- **NPC confirmation is service-guarded.** `VoteService.enterNpcConfirmation` is the only path that should persist `npcConfirmation`; it rejects non-`npc_pending` elections, elections without `requiresNpcConfirmation`, non-position/appointment election types, and tally values that are not finite non-negative integers.
- **Favour balance mutations are atomic.** API favour transactions and starting faction grants use the `favour_balances_player_category_unique` index with `INSERT ... ON CONFLICT DO UPDATE`; bot grant/spend flows use `db.transaction` with `sql\`balance ± ${amount}\`` UPDATE-then-INSERT-fallback. Spend uses a conditional UPDATE (`gte(balance, amount)`) to enforce sufficient funds in a single statement. Mirrors `grantBulk.ts`.
- **Web favour responses are flat-enriched.** `/api/favours/balances/:playerId`, `/api/favours/balances`, and favour history responses expose denormalized labels such as `categoryName`, `categoryEmoji`, `playerName`, and `discordUsername` rather than nested `category`/`player` objects. Web favour views should render those flat fields first and only fall back to UUIDs when the API genuinely did not provide a label.
- **Private favour visibility relies on the runtime gate.** Discord's `default_member_permissions` is parent-command-scoped, so once staff-only favour actions (`/favour leaderboard`, `/favour grant`, `/favour grant-bulk`, `/favour remove`, `/favour check`, `/favour category-*`) became subcommands under the unified `/favour` parent, Discord-level discovery gating could no longer hide them without also hiding player-facing `/favour balance`. The boundary is now the runtime `isStaff` check at the top of each handler — keep that in every staff-only favour subcommand, and `leaderboard.test.ts` asserts the description still carries the `staff only` hint so a maintainer cannot silently drop the runtime gate.
- **Starting-age favour bonuses are automatic when a faction category exists.** `createCharacter` and both Discord character-create paths call `grantStartingFactionFavours`, which finds an active favour category whose name or short name exactly matches the selected faction's name or short name and writes a `system` transaction. `startingFavoursGranted` flips true only after the transaction succeeds. If no category matches, character creation still succeeds and the bonus remains visible for staff correction.
- **Character dossiers hide favour balances.** `/character view` is player-facing and should not fetch or render favour balance data. Keep balances in `/favour balance` for self-service and `/favour check` for staff inspection.
- **Direct-uploaded character portraits keep their source message.** `/character create` strips Discord attachment CDN signature params (`ex`, `is`, `hm`) before storing portrait URLs, percent-encodes parentheses for `[View Image](...)`, and must not delete the uploaded message because the Discord attachment depends on its source message staying available.
- **`ballots(electionId, voterId)` uniqueness** is also a schema TODO. `VoteService.castBallot` does a SELECT pre-check and surfaces "already voted" if the row exists or a Postgres `23505` is raised.
- **Faction `dissolve` is transactional.** All five ops (member select, null player factionId, event-log insert per member, null parties.factionId, set factions.isActive=false) wrap in `db.transaction`.
- **Character name uniqueness is checked twice** — early UX hint, plus a re-check immediately before insert plus a `23505` catch in the persist block (modal flow has minutes between the two).
- **Character names are DB-unique.** `players.character_name` carries a unique constraint so concurrent bot/API creates cannot duplicate names. User-facing create routes must translate Postgres `23505` into `409`/friendly conflict messages instead of a generic server/database failure. Bot `/character create` updates OAuth placeholder rows with `WHERE character_name IS NULL` and checks the returned row so a second in-flight create from the same Discord account cannot overwrite the first finished character.
- **Pagination collector `end` handler uses `interaction.editReply`** — works for ephemeral messages too. `message.edit` would 404 on ephemeral.
- **Modal handlers re-check permissions for restricted election types** (`legislative_vote`, `position_election`, `appointment_confirmation`). Slash command perms don't carry through to modal submits.
- **Reaction-mode votes default where supported.** `elections.useReactions` (boolean) flags a vote whose ballots come from emoji reactions on the public embed instead of ephemeral buttons. `/vote create` defaults to reactions for `yea_nay_abstain` (👍/👎/🤐) and `fptp` (1️⃣..9️⃣ by candidate registration order); methods that cannot fit reactions default to buttons, and an explicit `interface:buttons` override remains available. Cast path is `events/messageReactionAdd.ts`, which (1) fast-paths via `discordMessageId` lookup, (2) requires an existing player character, not merely an OAuth placeholder row, (3) stores FPTP ballots with the candidate `playerId` rather than the candidate registration row id, (4) replaces the prior ballot atomically (delete-then-insert in a transaction — reaction votes are mutable until close), and (5) leaves reactions visible as the public voting record. Reaction instruction copy is centralized in `buildReactionVoteInstructions`; do not tell voters their reaction is removed after recording. Reaction-vote success confirmation DMs are off by default; set `REACTION_VOTE_CONFIRMATION_DMS=true` to opt in, and when enabled they should only confirm the recorded choice without extra reminders that the reaction remains public. Bot needs `Partials.{Message,Channel,Reaction,User}` on the client to receive reactions on messages cached before startup. `/vote close` for reaction-mode votes inlines a tally (yea/nay or FPTP only — bot still doesn't import API tally strategies), keys FPTP counts by candidate player id, edits the original embed in-place with results, and keeps the reactions in place so anyone can inspect who voted for what. Vote reference commands use `findElectionByReference`, so users may pass a full election ID, the 8-char prefix shown by `/vote list`, or an exact title.
- **Party join reaction boards are public self-service only.** `pnpm --filter @hansard/bot post:party-join` posts the open-party board, defaulting to SCORP3 channel `1501608247411609646` unless `PARTY_JOIN_CHANNEL_ID` is set; set `PARTY_JOIN_MESSAGE_ID` after posting to pin reactions to that exact board. `pnpm --filter @hansard/bot refresh:party-join` edits the current board in place and re-seeds its reactions. The reaction handler lists/accepts only active non-invite-only parties, parses the clicked emoji from the posted embed line, requires a live character, wraps the party update plus `party_change` log in one transaction, and serializes joins per Discord user before best-effort role sync. Without `PARTY_JOIN_MESSAGE_ID`, it only accepts the newest bot-authored join board among recent channel messages so stale/spoofed embeds do not stay actionable. Open-party `/party create` refreshes the current join board in place and preserves existing non-neutral party emoji assignments before seeding any new reactions; invite-only parties remain omitted. Party join emoji assignment is hue-aware, so dark saturated party hex colours map to red/blue/green/purple/etc. rather than collapsing to black, and refreshes clear stale board reactions before re-seeding the current options.
